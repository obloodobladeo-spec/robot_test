# 핵심 개념 복습

이 문서의 수치 예시는 원리를 설명하기 위한 것입니다. 실제 동작 상수는 해당 프로젝트의 현재 코드·CubeMX 설정을 우선합니다. 목표는 LED나 시험 모터를 돌리는 데서 끝나지 않고, 명령→측정→제어→피드백의 연결을 이해하는 것입니다.

## 타이머·PWM·메인의 서로 다른 주기

타이머 입력 클럭은 카운터를 움직이는 기준입니다. 내부 클럭을 쓰는 일반 타이머의 카운터 속도는 타이머 클럭을 PSC+1로 나눈 값이고, UP 카운터는 0부터 ARR까지 세므로 한 주기는 ARR+1카운트입니다. CPU 주파수와 타이머 주파수는 클럭 트리·APB 분주 설정에 따라 다를 수 있습니다.

- 타이머 클럭84MHz, PSC=83: 카운터는1MHz, 한 칸은1µs.
- 여기에 ARR=9999: 10000칸이므로10ms마다 한 주기.
- 타이머 클럭84MHz, PSC=0, ARR=4199: 4200칸이므로20kHz PWM.

타이머가 끝날 때마다 CPU가 명령을 내려 숫자를 세는 것은 아닙니다. 하드웨어가 계속 세고, 주기 종료 시 활성화한 인터럽트가 실행됩니다. 일반적인 단일 코어 실행에서는 인터럽트가 메인을 잠시 중단하고 콜백을 처리한 뒤 메인으로 돌아옵니다.

PWM mode1·High polarity의 단순한 경우 CNT<CCR 구간이 High입니다. 듀티를 percent로 관리하면 다음 관계로 CCR을 씁니다.

```text
CCR = (ARR + 1) × duty_percent / 100
ARR=4199, duty=20% → CCR=840
```

`__HAL_TIM_GET_AUTORELOAD()`는 ARR 레지스터를 읽습니다. `__HAL_TIM_SET_COMPARE()`는 해당 채널의 CCR을 설정합니다. 듀티0~100% 허용 범위는 별도로 제어해야 하며 현재 모터 코드는0~50%를 사용합니다.

CCR preload를 켜면 새 비교값은 먼저 대기 레지스터에 들어가고 업데이트 이벤트에서 반영됩니다. 반영 전에 두 번 쓰면 중간 값이 별도로 출력되지 않고 마지막 값이 남습니다. 메인에서 밝기를10ms마다 바꾸더라도20kHz PWM은 그동안 하드웨어에서 약200주기를 계속 생성합니다.

`HAL_Delay()`는 CPU의 메인 진행을 기다리게 하지만 PWM 하드웨어는 계속 동작할 수 있습니다. `HAL_GetTick()`의 차이로 경과 시간을 확인하면 메인을 막지 않고 주기 작업을 할 수 있습니다. `if (now-last >= period)`에서 조건이 충족된 뒤 기준 tick을 저장하지 않으면 다음 while에서도 계속 조건이 참이 됩니다.

## 입력 캡처·static·volatile

입력 캡처는 신호 에지가 올 때 CNT를 CCR에 저장합니다. 첫 캡처는 기준값만 만들고 두 번째부터 차이를 계산합니다. 1MHz 카운터에서 두 캡처 차이가1000이면 주기는1000µs, 주파수는1kHz입니다. 경계를 넘으면 카운터 범위까지 고려해야 합니다.

함수 내부 `static uint32_t previous`는 함수가 다시 호출돼도 매번 초기화되지 않습니다. 첫 초기화 뒤 값을 유지하므로 이전 캡처를 기억할 수 있습니다. 일반 지역 변수는 호출마다 새로 만들어집니다.

`volatile`은 ISR·하드웨어 등 코드 밖에서 값이 바뀔 수 있다는 접근 의미입니다. 단순히 디버거에 값을 보이게 하거나 함수 호출 사이 값을 보존하는 기능이 아닙니다. 메인만 사용하는 값에 미리 붙이지 않습니다. `pending++`와 `pending--` 같은 읽기-수정-쓰기는 volatile만으로 경쟁을 해결하지 못합니다. 저장값을 메인으로 넘길 때 원자성과 덮어쓰기 가능성도 확인해야 합니다.

디버거는 정지한 위치의 유효 범위와 최적화 상태에 따라 지역 변수가 보이지 않을 수 있습니다. 콜백 안의 static도 그 유효 범위에서 확인하고, 최적화된 빌드에서는 소스에 쓴 대로 메모리·명령이 유지되지 않을 수 있습니다.

## 엔코더와 속도

엔코더는 RPM 숫자를 보내지 않고 A/B 신호를 바꿉니다. 두 신호의 순서로 방향을 구하며 TI12의 ×4 방식에서는 A/B 상승·하강을 합해 한 신호 주기당4count를 셉니다. 모터가 빠를수록 신호가 빠릅니다. 모터 PWM의20kHz와는 다른 주파수입니다.

메인에서100ms마다 CNT를 읽어도 그 사이의 카운트는 타이머가 계속 누적합니다. while문 자체가100ms마다 한 번 도는 것은 아닙니다. 정지 상태의 작은 변동, 엔코더 부호·배선, 카운터 경계는 각각 확인합니다.

16비트 카운터의 단순 차이가32767보다 크면65536을 빼고, −32768보다 작으면65536을 더해 경계를 보정할 수 있습니다. 이 방법은 한 표본 사이 실제 변화가 반 범위보다 작다는 조건이 필요합니다. 정·역방향의 이름을 정하는 코드와 경계 보정은 별개입니다.

```text
구간 회전량 = delta_count / counts_per_turn
구간 거리 = 구간 회전량 × 바퀴 둘레
속도 = 구간 거리 / 실제 구간 시간
```

측정 시간은 설정한 목표 주기만 믿지 않고 실제 tick 차이를 사용합니다. 한 바퀴당 실측 count는 이미 사용한 디코딩 방식이 포함돼 있으므로 다시 ×4를 하지 않습니다. 바퀴가 헛돌면 엔코더로 구한 거리와 실제 이동 거리가 다릅니다.

## P·I 제어의 계산 흐름

제어 오차는 `e(t)=r(t)−y(t)`로 둡니다. 목표가100mm/s, 실제가40mm/s라면 오차는+60mm/s입니다. 양의 오차는 목표에 못 미쳐 출력을 더 요구하는 방향입니다.

현재 학습한 위치형 PI의 이산 계산 구조는 다음과 같습니다.

```text
P = Kp × error
I_candidate = I_previous + Ki × error × dt
output_candidate = P + I_candidate
```

참고: [Microchip PI 제어 설명](https://onlinedocs.microchip.com/oxy/GUID-69278EBA-9F00-4CEE-8103-2998236856BD-en-US-2/GUID-68C13886-A5D4-4274-9410-D1AE3D79CFF9.html). 현재 코드의 출력 단위는 duty percent이며 dt는초입니다. 자료마다 연속/이산 표현과 계수 정의가 다르므로 수치만 복사하지 않습니다.

예를 들어 Kp=0.1, Ki=0.1, dt=0.1초, 이전 적분0, 오차60이면 P=6%, 이번 적분 증가0.6%, 제한 전 출력6.6%입니다. 다음 계산에서는 **새로 측정한 오차**로 P를 다시 만들고 I에는 새 증가분을 누적합니다. 이전 듀티에 P를 계속 더하는 구조가 아닙니다.

순수 P만으로는 목표에 가까워져 오차가 작아질수록 출력도 작아져 오차가 남을 수 있습니다. I는 남는 오차를 시간에 걸쳐 누적해 필요한 출력을 유지하도록 돕습니다. Kp를 크게 하면 같은 오차에 대한 즉시 반응이 커지고, Ki를 크게 하면 같은 오차·시간에 쌓이는 적분이 커집니다. 과하면 진동·과도 응답·느린 복귀가 생길 수 있습니다.

anti-windup은 출력 제한을 더 넘기는 방향의 적분 저장을 막습니다. 상한에서 양의 오차가 계속 있어도 적분을 무한히 쌓지 않습니다. 반대 방향 오차가 생기면 포화에서 빠져나오는 적분은 허용할 수 있습니다. 코드의 실제 조건과 제한값을 함께 읽어야 합니다.

현재 가속도 제한100mm/s², 표본0.1초이면 제어 목표는 한 번에 최대10mm/s씩 바뀝니다. 사용자 목표와 점진적으로 바뀌는 제어 목표를 구분합니다. 이는 Ki와 다른 기능입니다.

## 차동구동과 바퀴 오도메트리

좌우 구동축 중간점에서 선속도v, 각속도w, 윤거b를 쓰면 다음과 같습니다. 길이 단위를 먼저 통일합니다.

```text
left_target  = v − w × b / 2
right_target = v + w × b / 2
```

참고: [ROS 2 control의 이동 로봇 운동학](https://control.ros.org/iron/doc/ros2_controllers/doc/mobile_robot_kinematics.html). 바퀴4개를 독립 구동하는 메카넘 모델에 이2륜 식을 그대로 적용하지 않습니다.

현재 b=230mm, v=0, w=+0.3rad/s이면 왼쪽−34.5mm/s, 오른쪽+34.5mm/s입니다. w에50을 주면50rad/s이므로 매우 큰 목표이며, 현재 제한에 걸릴 수 있습니다. 한쪽은+200, 다른 쪽은−200이 되는 현상은 이 부호와 제한을 함께 봐야 합니다.

한 구간에서 좌우 이동량으로 중심 이동과 방향 변화를 구하고, 구간 중간 방향을 사용해 x/y에 누적하는 방식으로 바퀴 odom을 계산했습니다. yaw가0이 아닐 때는 전진해도 y가 함께 변할 수 있습니다. 접지·허브·바퀴 크기 오차가 누적되므로 지면의 실제 궤적과 비교해야 합니다.

## ROS 데이터 흐름과 시간

`/cmd_vel`은 목표, `/odom`은 추정 위치·방향·속도·공분산을 담는 메시지, TF는 좌표 사이의 위치·방향 관계입니다. TF에 속도·공분산이 모두 들어 있는 것은 아닙니다. `/odom`을 발행했다고 TF가 자동으로 생기지도 않습니다.

현재 브리지는 같은 위치·방향·시각으로 odom과 `odom → base_link`를 각각 발행합니다. ROS Node의 `get_clock()`은 기본적으로 시스템 시각 기반 ROS clock입니다. `use_sim_time`은 일반 ROS 노드가 제공하는 기본 매개변수이며 true이면 `/clock`을 사용합니다. 통신 시간 초과에는 시각 변경과 무관한 `time.monotonic()`을 사용했습니다.

URDF는 링크·joint의 관계를 정하고 robot_state_publisher가 TF로 제공합니다. fixed joint는 axis가 필요 없고, continuous joint는 회전축을 지정합니다. mesh는 파일에 저장한 원점을 사용하며 자동으로 형상 중심에 맞추지 않습니다.

## LaserScan을 읽기 전에 확인한 것

가짜3점으로 메시지와 TF 표시를 익혔지만 실제 센서 발행 검증과 구분했습니다. 실제 C1은 USB 장치·권한·드라이버·frame_id·배열·주기를 확인한 뒤 Python 구독으로 넘어갔습니다.

`ranges`는 거리 배열, `angle_min`은 첫 방향, `angle_increment`는 다음 원소까지의 각도입니다. C1 드라이버가 보간·각도 보상해 만든720개 값이 센서의 독립 실측720개와 반드시 같은 뜻은 아닙니다. 배열 길이·회전 주기·센서 원시 샘플 속도를 구분합니다.

초당10개 메시지를 받는 콜백과1초에 한 번만 출력하는 로그 제한은 다릅니다. 앞으로 정면 거리·장애물 판단을 추가할 때는 무효값·배열 범위·좌표 방향을 확인해야 하며, 지금 코드는 아직 거리로 모터를 멈추는 기능이 아닙니다.
