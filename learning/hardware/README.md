# 자율주행 로봇 하드웨어 기록

최종 갱신: 2026-10-23

## 구성

- 제어 보드: STM32F446RE
- 상위 컴퓨터: NVIDIA Jetson Orin Nano 8GB Developer Kit
- 현재 모터: 2개
- 추가 하중: 2026-10-20 사용자가 무게를 올렸다고 확인했다. 추가 질량·배치 위치·정확한 적용 시점은 미측정이다. 직전 10초 회전 시험의 반응 지연을 해석할 때 하중 변경을 고려하며, 앞선 시험과 동일 하중이었다고 가정하지 않는다.
- 구동 배치: 후륜 구동으로 변경함. 2026-10-20 사용자 확인 기준으로 좌우 구동 바퀴는 차체 뒤쪽에 있다.
- 모터 드라이버: 정상 MDD10A 사용
- 모터 전원: DXF 3S LiPo, 11.1V 7200mAh 100C, 완충 12.6V
- 전원 배선: XT60 → 12AWG 인라인 퓨즈(15A) → WAGO → 16AWG → MDD10A
- 배터리 알람: 셀당 3.5V
- 벤치 테스트 중 Jetson은 전용 LiteOn 19V 2.37A 어댑터 사용

주의: 이전 MDD10A 한 개는 측정 중 프로브 단락으로 손상되었으므로 다시 사용하지 않는다.

### 구동 배치 변경과 좌표 기준 (2026-10-20)

- 현재는 후륜 구동을 기준으로 해석한다. 이전 사진만으로 전륜 구동이라고 설명한 내용은 현재 배치에 적용하지 않는다.
- 이상적인 차동구동 계산의 기준점은 좌우 후륜 구동 바퀴 사이의 중간점이다. 이 위치와 차체 기하학적 중심의 앞뒤 거리는 아직 측정하지 않았다.
- 윤거: **230mm**. 좌우 후륜 타이어의 폭 중심선 사이 거리이며, 2026-10-20 사용자가 측정값을 전달했다.
- 모터 좌우 배치: 차체 전진 방향 기준 **모터1=왼쪽 후륜, 모터2=오른쪽 후륜**. 2026-10-20 사용자 확인.
- 변경 후 차체 전진에 필요한 각 모터의 DIR 레벨과 전진 시 엔코더 부호는 다시 확인해야 한다. 이전 HIGH=전진·양수 피드백 기록만으로 변경 후 배치를 확정하지 않는다.
- 전방 보조 바퀴의 고정·캐스터 여부와 변경 후 실제 회전 중심·미끄러짐은 확인하지 않았다.
- 사용자 관찰(2026-10-20): 회전할 때 오른쪽 앞바퀴를 축으로 도는 것처럼 보인다. 당시 전진 명령, 좌우 후륜의 실제 측정 속도, 앞바퀴 형태와 접지 조건을 함께 확인하기 전까지 원인은 확정하지 않는다.

### 차체 회전 명령 비교 (2026-10-20)

- 동일한 Ki 비교를 양방향 각 20초 재측정했습니다. 지속 회전 관측 시각은 Ki=0.1에서 11.42~12.50초, 0.2에서 5.09~6.81초, 0.3에서 4.77~5.06초였습니다. Ki=0.3의 후반 평균은 목표 ±34.5mm/s에 가까웠으나 속도 변동은 남았습니다. 종료 후 정지·Ki=0.1 복구를 확인했습니다. [Ki 비교 재측정 기록](../study_notes/assets/motor_tests/2026-10-20/033539_ki_sweep/README.md)

- 추가 하중 상태에서 Kp=0.1을 유지하고 Ki=0.1·0.2·0.3으로 양방향 각 20초 회전 시험을 수행했습니다. 목표 절반 이상 속도가 3회 연속 관측되기까지 양쪽 합산 범위는 각각 11.25~12.98초, 6.56~8.06초, 4.51~6.28초였습니다. Ki 증가 시 지연은 줄었으나 속도 변동과 과도 응답은 남았습니다. 최종 이득은 확정하지 않았으며 종료 후 정지·Ki=0.1 복구를 확인했습니다. [하중 추가 Ki 비교 기록](../study_notes/assets/motor_tests/2026-10-20/033054_ki_sweep/README.md)

- 전진 0, 회전 ±0.3rad/s를 각 20초 적용했습니다. Kp=0.1, Ki=0.1, 가속도 제한 100mm/s², 듀티 상한 50%를 유지했습니다. 좌우 목표는 ±34.5mm/s로 확인했습니다.
- +0.3의 마지막 5초 평균: 왼쪽 -32.00mm/s·듀티 32.08%, 오른쪽 +37.86mm/s·듀티 30.40%.
- -0.3의 마지막 5초 평균: 왼쪽 +25.23mm/s·듀티 35.48%, 오른쪽 -35.64mm/s·듀티 26.95%.
- 초기 8초 기록은 적분 출력이 충분히 쌓이기 전의 출발 과정이었습니다. 20초에서도 속도 변동과 좌우 차이가 남아 정상상태 수렴을 확인하지는 못했습니다.
- 앞바퀴 형태·실제 차체 회전 중심은 직접 확인하지 않았습니다. 시험 후 차체 명령과 양쪽 모터 출력은 0으로 정지 확인했습니다.
- [회전 시험 전체 기록](../study_notes/assets/motor_tests/2026-10-20/025651/README.md)

### 앞쪽 보조 바퀴 테이프 적용 비교 (2026-10-20)

- 추가 사용자 확인: 앞쪽 보조 바퀴의 타이어 접촉면 전체를 절연테이프로 감았다. 사용자는 회전 반응 변화를 보고 앞바퀴 접지·마찰이 문제에 기여했다고 판단했다. 초기 시험별 테이프 적용 면적과 실제 마찰계수는 계측하지 않았다.
- 사용자가 앞쪽 보조 바퀴에 절연테이프를 적용한 뒤 동일한 전진 0·회전 ±0.3rad/s·각 20초 조건으로 재시험했습니다. 전후 펌웨어 해시는 동일합니다.
- 적용 후 마지막 5초 평균: +0.3에서 왼쪽 -28.29mm/s·듀티 33.13%, 오른쪽 +36.46mm/s·듀티 31.32%. -0.3에서 왼쪽 +34.80mm/s·듀티 35.78%, 오른쪽 -31.37mm/s·듀티 29.79%.
- -0.3에서 왼쪽 평균 속도는 목표에 가까워졌으나 양방향 공통 개선과 필요한 듀티 감소는 확인하지 못했습니다. 실제 마찰계수와 차체 회전 중심 변화는 미측정입니다.
- 시험 후 차체 명령과 양쪽 모터 출력을 0으로 정지 확인했습니다.
- [테이프 전후 비교 기록](../study_notes/assets/motor_tests/2026-10-20/030432/README.md)
- 같은 설정으로 재시험: +0.3에서 왼쪽 -39.83mm/s·듀티 31.06%, 오른쪽 +37.94mm/s·듀티 31.00%. -0.3에서 왼쪽 +34.88mm/s·듀티 32.84%, 오른쪽 -37.77mm/s·듀티 28.01% (각 20초 중 마지막 5초 평균).
- 재시험에서는 앞선 왼쪽 저속 양상이 일관되게 재현되지 않았습니다. 속도 변동은 남아 있으며 모터 자체의 성능 차이나 접지 영향은 아직 분리하지 않았습니다. [재시험 기록](../study_notes/assets/motor_tests/2026-10-20/031011/README.md)
- 이후 각 10초 회전 시험의 마지막 2초 평균: +0.3에서 왼쪽 -1.60mm/s·듀티 32.33%, 오른쪽 +5.58mm/s·듀티 30.01%. -0.3에서 왼쪽 +7.21mm/s·듀티 30.49%, 오른쪽 -14.96mm/s·듀티 28.84%였습니다. 이번 10초 안에서는 목표 미도달이며 출발 과정과 접지 부하를 구분해야 합니다. 종료 후 차체 명령과 양쪽 출력 0을 확인했습니다. [10초 회전 기록](../study_notes/assets/motor_tests/2026-10-20/032404/README.md)

### 테이프 적용 상태에서 전후진 확인 (2026-10-20)

- 회전 명령 0, 전진 +50mm/s와 후진 -50mm/s를 각각 8초 적용하고 단계마다 정지했습니다.

## 휠·허브 결합과 모터 속도 변동 검사 (2026-10-18)

### 사용자 관찰

- 기존 바퀴 지름은 110mm로 크며, 휠 허브는 사용자가 3D 프린터로 별도 제작했다.
- 사용자가 확인한 허브 결합 상태가 좋지 않다. 편심·유격·체결 위치·주변 간섭을 추가 확인해야 한다.
- 사용자는 현재 모터의 힘이 충분히 강하지 않다고 관찰했다. 바닥에서 한 모터를 20% 듀티로 구동할 때 차체가 출발하지 못한 사례가 있다.
- 이는 현재 하중·마찰·바퀴 크기·출력 조건에서의 관찰이다. 모터의 정격·스톨 토크나 전류를 실측한 결과는 아니다. 두 모터 동시 구동 및 최종 하중의 토크 여유는 미검증이다.

### 시험 조건과 실제 측정

- 보드: ST-LINK에서 NUCLEO-F446RE, STM32F446xx를 확인했다. MCU 보드 전압 조회는 약 3.25V였으며 시험 중 배터리 전압·모터 전류는 별도 측정하지 않았다.
- 펌웨어: encoder_basic, STM32CubeF4 HAL, PWM TIM1_CH1/PA8, DIR PC0 HIGH, 엔코더 TIM2/PA0·PA1.
- 기존 모터 전원은 기록된 3S LiPo·15A 퓨즈·MDD10A 구성, MCU는 USB 전원. 사용자가 바퀴를 모두 띄웠다고 확인한 벤치 조건에서 비교했다.
- TIM1 20kHz, ARR=4199, 제어 간격 100ms. 고정 출력은 듀티 14.4%·실제 CCR1=604, PI는 Kp=0.2·Ki=0.1·목표 100mm/s·상한 20%.
- STM32CubeProgrammer CLI의 SWD HOTPLUG로 RAM·CCR1을 읽고 목표·이득을 RAM에서 변경했다. 이득 조정 준비 때 두 이득을 const에서 RAM 변수로 바꾸어 빌드·검증·업로드했고, 이후 휠 비교는 재업로드 없이 진행했다.
- 최초 고정 출력 약 18초, 휠 제거·새 휠·기존 휠 재장착의 고정 출력 각 약 18초, 각 PI 약 22~24초. 아래 범위·평균은 각 시험의 마지막 약 7초 조회 표본이다.
- 속도는 실측 2465.2count/출력축 1회전과 기존 둘레 345.6mm로 환산했다. 휠 제거 시에는 가상 선속도이며, 다른 휠 지름은 재측정하지 않았다. RPM 및 count도 함께 기록했다.

| 같은 기존 모터의 상태 | 고정 CCR1=604 속도 범위 | PI 목표 100의 속도 범위 | PI 조회 평균 |
| --- | --- | --- | --- |
| 기존 휠 최초 장착 | 약 72.90~126.17mm/s | 약 88.32~109.35mm/s | 약 100.09mm/s |
| 휠 제거 | 약 123.37~124.77mm/s | 약 96.73~102.34mm/s | 약 99.81mm/s |
| 다른 휠 장착 | 약 121.97~123.37mm/s | 약 96.73~102.34mm/s | 약 99.86mm/s |
| 기존 휠 재장착 | 약 113.56~123.37mm/s | 약 95.33~102.34mm/s | 약 99.86mm/s |

- 다른 모터로 교체한 별도 시험도 진행했으며 PI 평균 약 99.84mm/s, 범위 약 96.73~102.34mm/s였다. 그 모터와 기존 모터의 휠 장착 조건을 완전히 동일하게 통제한 토크 성능 비교는 아니다.
- 고정 CCR에서도 최초 속도 변동이 남았으므로 PI 계산만으로 생기는 현상으로 설명되지 않는다.
- 기존 모터에서 휠을 제거하거나 다른 휠로 교체하면 큰 변동이 줄었다. 기존 휠을 다시 장착했을 때도 최초의 큰 변동은 재현되지 않았다.
- 판단: 휠·3D 프린트 허브의 장착 상태 및 하중 영향이 주요 원인 후보다. 휠 불량·모터 고장을 확정하지 않았고 편심·불균형·간섭의 개별 원인은 분리 측정하지 않았다.
- 각 시험 후 목표 0, 측정 속도 0, 듀티 0, I 출력 0, CCR1=0을 읽어 정지를 확인했다. 단일 모터 벤치 확인이며 바닥 주행·최종 하중은 별도 검증이 필요하다.

### STM32 전원 구성(계획, 미검증)

ST-LINK 식별에서 `NUCLEO-F446RE`임을 확인했다. 아래 외부 전원 분기와 점퍼 설정은 아직 검증하지 않았다.

- 3S LiPo는 완충 `12.6V`이므로 STM32의 `5V`, `3.3V` 또는 Nucleo `VIN`에 직접 연결하지 않는다.
- 계획 배선: 배터리 → XT60 → 12AWG 인라인 퓨즈(`15A`) → WAGO 분기 → STM32 전용 분기 퓨즈 → DC-DC 벅 컨버터 → Nucleo `E5V`
- 벅 컨버터 권장 조건: 입력 정격 최소 `24V`(가능하면 `36V`), 출력 `5.0V`, 연속 출력 `2A` 이상, 역극성 보호
- STM32만 전원을 공급할 때의 분기 퓨즈 후보는 `1A`이다. 엔코더나 센서를 같이 공급하면 실측 전류와 기동 전류를 확인한 후 확정한다.
- STM32 분기 배선은 짧은 `20~22AWG`를 후보로 하고, 커넥터 정격은 퓨즈 정격보다 크게 선정한다.
- WAGO 음극에서 MDD10A 전원 GND와 벅 컨버터 `IN-`를 별도 배선하고, 벅 `OUT-`와 STM32 GND를 연결한다. 모터 고전류 리턴이 STM32 접지선을 통과하지 않도록 한다.
- `NUCLEO-F446RE`가 맞으면 외부 `5V` 공급 전 `JP5`를 `E5V` 위치로 설정하고, `E5V`가 `4.75~5.25V` 범위인지 확인한다.
- 외부 전원과 ST-LINK USB를 함께 사용할 때는 ST UM1724의 `JP5` 설정과 전원 인가 순서를 따른다.
- 실제 배선 전 벅 컨버터만 연결하여 무부하 출력을 `5.0V`로 조정하고 극성을 확인한다.

## Jetson 설치 상태

- 현재 JetPack: **6.2.3** (L4T 36.5.2 기준)
- L4T: **36.5.2**
- UEFI/펌웨어: **36.5.2**; 커널 `5.15.199-tegra`
- CUDA compiler: 이전 측정 **12.6.68**; 이번 업데이트 후 컴파일러 버전은 재측정하지 않음
- 전원 모드: `NV Power Mode: 25W`, 모델 ID 1
- 현재 부팅 장치: Samsung MZVLQ128HCHQ-00B 128GB NVMe SSD; 기존 SanDisk Ultra 64GB microSD는 분리 보관
- 인식 메모리: 약 7.4GiB(tegrastats 기준 총 7620MB)

펌웨어 갱신 과정:

1. JetPack 5.1.3 SD 이미지로 부팅했다.
2. `nvidia-l4t-jetson-orin-nano-qspi-updater`로 QSPI 부트로더를 갱신했다.
3. JetPack 6.2.1 SD 이미지를 새로 기록했다.
4. 부팅 후 L4T와 부트로더가 36.4.4이고 슬롯 상태가 정상임을 확인했다.

초기 UEFI에서 `Orin NX`, RAM 0MB로 표시되던 현상은 구형 펌웨어 표시 문제였고, 펌웨어 갱신 후 Orin Nano와 약 8GB 메모리가 정상 표시되었다.

## 브라우저 관련 확인 내용

브라우저 문제는 Jetson 본체의 CPU/GPU 연산 불량과 분리해서 판단한다.

- Ubuntu 기본 Snap Chromium은 당시 JetPack 6.2.1/L4T 36.4.4 환경에서 Snap 보안·커널 호환 오류로 정상 실행되지 않았다.
- Epiphany(GNOME Web) 42.4는 일반 페이지를 열 수 있었지만 ChatGPT 로그인처럼 동작이 추가될 때 SIGSEGV로 종료되었다.
- Epiphany 로그에서 `NvRmMemInitNvmap failed`, `Memory Manager Not supported`, 오류 196626 및 WebKitGTK/JavaScriptCore 스택을 확인했다.
- 여러 WebKit DMA-BUF, SHM, compositing 및 소프트웨어 렌더링 우회 옵션으로도 Epiphany 충돌은 해결되지 않았다.
- Flatpak Chromium은 설치 및 웹 접속에 성공했다. 다만 GPU/EGL 초기화 실패 후 소프트웨어 경로로 동작할 수 있어 체감 속도가 느릴 수 있다.
- 현재 방침: Jetson에서는 브라우저를 주 작업 수단으로 사용하지 않고, Windows에서 개발·검색하고 Jetson은 연산 및 로봇 실행 장치로 사용한다.

브라우저 문제만으로 Jetson 하드웨어 불량이라고 판단하지 않는다.

## microSD와 저장장치

- microSD 측정값: 순차 읽기 약 31.8MB/s, 순차 쓰기 약 29MB/s, 랜덤 쓰기 약 0.9MB/s
- 카드 리더가 USB 2.0일 가능성이 있어 순차 속도만으로 카드 불량을 단정할 수 없다.
- microSD의 낮은 랜덤 성능은 앱 실행, 브라우저 캐시, 패키지 설치 및 시스템 반응 속도를 늦출 수 있다.
- 2026-10-23 실제 장착한 SSD는 Samsung MZVLQ128HCHQ-00B 128GB이다. 기존 Windows 파티션 삭제 후 SD 시스템을 복사하여 NVMe 단독 부팅을 확인했다. 새 OS를 설치한 것은 아니다.
- NVMe에서 NVIDIA r36.5 저장소를 사용해 L4T 36.4.4 → 36.5.2로 업데이트하고 재부팅 검증을 완료했다. SD는 기존 시스템 상태로 보관하지만 QSPI 펌웨어는 보드 공용이므로 완전히 독립적인 복구 매체로 검증한 것은 아니다.

## C1 라이다 수령 후 핵심 기능 확인 (2026-10-23)

- 대상: 당일 도착한 SLAMTEC RPLIDAR C1. RoboStudio에서 `C1M1`로 인식.
- 구성: Windows 노트북 USB → 제공된 USB-UART 어댑터 → C1. Jetson에는 아직 연결하여 검사하지 않았다.
- 프로그램: 공식 해외 지원 페이지의 RoboStudio 2.1.1-rtm 압축 배포본에서 `robostudio.exe` 실행.
- USB 인식: Silicon Labs CP210x USB to UART Bridge, COM5, 장치 관리자 정상 상태. 연결 설정 460800bps, 장치 모델·시리얼 번호 조회 성공.
- 스캔 화면에서 9.80Hz(588rpm) 회전과 여러 방향의 주변 물체·벽 윤곽 수신 확인. 정확한 연속 운전 시간과 회전 속도 변동 범위는 기록하지 않았다.
- 손으로 가렸을 때 주변 점군이 사라지거나 가까운 점으로 변하는 반응을 화면에서 확인했다.
- 사용자 거리 비교: 약 89cm 떨어진 냉장고와 약 114cm 떨어진 벽이 실제 거리와 비슷하게 표시됐으며, 사용자는 오차가 약 ±30mm라고 보고했다. 원시 측정값·표본 수·평균·표준편차를 수집한 정량 검증은 아니다.
- 제조사 C1M1-R2 데이터시트 기준: 거리 정확도 ±30mm(25°C, 표적 반사율 10~90% 조건), 거리 해상도 15mm. 사용자 관찰은 이 정확도 수치와 비슷하지만, 반복 정밀도와 전 구간 정확도를 인증한 것은 아니다.
- 소비전력은 미측정. 제조사 사양 참고값은 5V·10Hz에서 통상 230mA, 최대 260mA(약 1.15W·1.30W), 기동 전류 통상 800mA(약 4W)이며 기동 최대값은 명시되지 않았다. USB 전력계를 통한 실측은 실시하지 않았다.
- 사용자는 Orin Nano USB 포트 발열에 관한 다른 사용자의 리뷰를 언급했다. 본인 장치에서 해당 발열을 측정·확인한 사실은 없으며 불량 증거로 기록하지 않는다.
- 결론: USB 통신·회전·스캔·가림 반응·간이 거리 비교에서 초기 불량 징후는 관찰되지 않았다. 연속 사용 중 무중단 여부는 명시적으로 확인받지 않았다.
- 사용자 요청으로 오늘 작업 종료. 추가 라이다 측정, 필요 시 소비전력·USB 포트 발열 확인, Jetson/ROS 2 연결은 다음에 진행한다.

- 각 모터의 전진 DIR 레벨과 전진 시 엔코더 부호 확인 (모터1=왼쪽·모터2=오른쪽은 사용자 확인)
- 전방 보조 바퀴의 고정·캐스터 형태 확인 및 후륜 구동 상태에서 실제 회전 중심·미끄러짐 관찰
- 외부 전원 전환 전 보드의 `E5V` 핀과 `JP5` 설정 확인
- 3D 프린트 휠 허브의 축 결합·유격·편심·체결 위치 및 타이어·차체 간섭 확인
- 최종 하중에서 양쪽 모터 출발·회전 성능, 모터 전류와 토크 여유 확인
- STM32와 엔코더·센서의 연속/기동 전류 측정 후 분기 퓨즈 정격 확정
- DC-DC 벅 컨버터 모델, 입력/출력 정격, 역극성 보호, 배선·커넥터 정격 확인
- STM32 전원 분기 완성 후 무부하 `5V`, 유휴/STM32 부하, 모터 가감속·역전 중 최저 전압과 리셋 여부 검사
- C1 라이다 추가 측정·Jetson/ROS 2 연결: Windows 핵심 기능·간이 거리 비교는 2026-10-23 확인. 연속 사용 중 끊김과 정량 거리 측정은 미확인. 추가 작업은 사용자 요청으로 다음에 진행
- 카메라 연결 및 영상 입력 검사
- USB 3 저장장치로 실제 전송 속도 검사
- 유선 또는 무선 네트워크의 장시간 안정성과 처리량 검사
- 정상 종료와 재부팅을 2~3회 반복 확인
- 실제 로봇 조립 후 모터 구동 중 Jetson 전원과 통신 안정성 검사
- 필요할 때 Jetson에 Codex CLI를 설치하고 Windows 앱에서 SSH 연결 구성

## 운용 방향

- STM32: PWM, 방향 제어, 엔코더 계수와 실시간 모터 제어 담당
- Jetson: 카메라, YOLO/TensorRT, 센서 융합, 경로 판단 등 병렬 연산 담당
- 모터 전원과 Jetson 전원은 분리하여 모터 노이즈와 전압 강하가 Jetson에 전달되지 않도록 한다.
- Jetson의 장점은 CUDA/TensorRT GPU 연산에서 얻으며, 일반 ROS CPU 작업만으로는 Raspberry Pi 대비 장점이 크지 않을 수 있다.
