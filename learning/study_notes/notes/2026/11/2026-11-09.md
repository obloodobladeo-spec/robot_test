# 2026-11-09: STM32 복습, 디버깅 분리, 바퀴·윤거 변경

## 현재 상태

학습의 목표는 ROS 주행 명령을 STM32 모터 제어와 연결하고, 엔코더 추정과 실제 이동을 검증하는 것이다.
현재 단계는 차체 개조 후 거리·방향 오차 재검증이며 IMU/EKF/SLAM/Nav2는 아직 구현되지 않았다.

사용자가 기존 바퀴로 복귀했다고 확인했다. 현재 구동 바퀴 지름은 110mm, 명목 둘레는345.6mm다.
좌우 구동 바퀴 중심 간격은 최종 정정값 **234mm**다. 이 값은 차체 외형 폭과 다르다.
새 차체 길이·폭·높이, 구동축과 차체 중심의 거리, 최종 라이다 위치는 아직 실측값을 받지 않았다.
라이다를 뒤에 둘 수 있는지 논의했지만 새 배치가 확정됐다고 기록하지 않는다.

## PI 및 제어 코드 복습

- `Motor_Update()`는 메인에서 약100ms마다 실제 경과 시간으로 실행한다. PWM20kHz와 다른 주기다.
- `target_speed_mm_s`는 최종 목표, `control_target_speed_mm_s`는 가속도 제한이 적용된 제어 목표다.
  가속도 제한100mm/s²에서 정확히100ms 구간이면 제어 목표가 최대10mm/s 변한다.
- 속도 오차는 제어 목표에서 실제 속도를 뺀다. 방향을 곱한 `control_error`로 PWM 크기 증가·감소를 계산한다.
- P 출력은 현재 오차에 Kp를 곱해 매번 새로 계산한다. 이전 P 출력에 계속 더하는 방식이 아니다.
- I 출력은 기존 적분 출력에 `Ki * control_error * dt_s`를 더한다. 오차0이면 증가량이0이며 기존 출력은 남는다.
- 조건부 적분 anti-windup은 출력 상·하한을 더 벗어나게 하는 I 후보의 저장을 거부한다.
  제한 범위로 복귀시키는 방향의 적분은 허용한다.
- `Motor_ApplyDuty()`가 합산 출력을0~50%로 제한하고 ARR+1에 듀티를 적용해 CCR을 갱신한다.
- 정지 시 목표·제어 목표·I·CCR을0으로 만든다. `speed_error=-speed_mm_s`는 정지 목표에 맞는 상태 기록이며
  이 정지 함수에서 오차로 별도 제동 출력을 계산하지 않는다. 엔코더 누적 카운트·로봇 위치는 초기화하지 않는다.
- 방향 전환 전 PWM0을 적용하고 엔코더 변화량0을 연속3구간 확인한 뒤 DIR을 바꾼다.
  엔코더 단선과 실제 정지를 구분하는 진단 기능은 아니다.

제어 오차·PI 원식 출처: [Microchip 공식 설명](https://onlinedocs.microchip.com/oxy/GUID-69278EBA-9F00-4CEE-8103-2998236856BD-en-US-2/GUID-68C13886-A5D4-4274-9410-D1AE3D79CFF9.html).

## UART 없는 테스트

원본 `encoder_basic`은 UART 제어를 유지한다. `encorder_test`에 동일한 제어 로직을 `main.c` 한 파일로 구성했다.
UART 초기화·송수신·콜백·파서·500ms 통신 시간 초과 정지를 제거했다.
입력은 디버거에서 변경하는 `linear_speed_mm_s`와 `angular_speed_rad_s`이며 두 변수는 volatile이다.
별도 manual_debug 스위치나 motor_bridge 실행은 필요 없다. 입력을 바꾸거나 리셋하기 전까지 명령이 유지된다.
기존 미완성 motor_control.c/.h는 보존하고 .c만 Debug·Release 빌드에서 제외했다.
CubeMX 설정과 누락된 타이머 HAL도 맞췄다. 자세한 실행·정지 순서는 테스트 README에 있다.

## 엔코더 재측정

조립 중 두 모터가 바뀐 것으로 보고 CPR을 모터1=2475.6, 모터2=2465.2로 임시 교환했다.
현재 바퀴를 기준으로 원시 CNT를 다시 측정할 예정이다. 새 측정 결과는 아직 없다.
같은 모터·감속기·엔코더에서 휠만 교환하면 CPR 자체는 원칙적으로 달라지지 않는다.

속도 명령을 모두0으로 두고 실행한 뒤, 각 바퀴의 시작·끝 카운트를 같은 방향10회전으로 기록한다.
모터1 원시값은 `htim2.Instance->CNT`, 모터2는 `htim3.Instance->CNT`다.
0 경계에서 순환하면 경계 보정이 필요하다. 원시 카운트는 설정된 둘레·CPR의 영향을 받지 않는다.
새 CPR과 최종 하중의 실제 구름 둘레는 별도로 확인한다.

## ROS와 URDF 반영 범위

STM32 두 프로젝트의 윤거는234mm, WSL 브릿지 `wheel_track_m`는0.234m다.
브릿지는 STM32가 보낸 x/y를 mm→m로 변환하고, 좌우 속도 차이로 각속도를 계산할 때도 윤거를 사용한다.
URDF 뒤 구동 바퀴 반지름은0.055m, y 위치는±0.117m다. 기존 앞 보조 바퀴의 위치·형상은 새 볼 캐스터 실측이 아니다.
저장소에서 이미 검증 기록이 있던 라이다 yaw=π와 bringup은 보존했다.
현재 WSL 작업본의 라이다 yaw=0과 저장소 기록이 다르므로 최종 실제 장착 방향으로 재확인해야 한다.
치수 동기화 과정에서 이 방향 차이를 임의로 덮어쓰지 않았다.
Jetson의 파일은 PC 수정으로 자동 갱신되지 않는다. Jetson에서도 브릿지 윤거를0.234로 맞추고 다시 실행해야 한다.

## 하중·바닥 흔들림 해석

사용자는 바닥 주행에서 차체의 좌우 흔들림을 관찰했다. 로그에는 좌우 속도 차이가 최대10mm/s인 표본이 있었다.
후속 로그는45/45에서49/49mm/s로 접근했고 표시된 좌우 차이는 최대1mm/s였다.
이 로그만으로 모든100ms 구간의 진동이나 원인을 확정하지 않는다. 원문이1Hz 피드백이므로 빠른 변동을 놓칠 수 있다.
큰 하중, 볼 캐스터·바닥 요철, 타이어 변형, 허브 간섭, 부하와 PI의 상호작용을 구분해야 한다.
고정 CPR/둘레 환산 오차와 순간 카운트 잡음은 다르다. 순간 피드백 오류는 PI를 통해 실제 PWM 변동을 만들 수 있다.
이번 변경에서 Kp/Ki·가속도·듀티 상한을 조정하지 않았다.

## WSL 통신 조사 요약

셧다운 후 CLI 데몬 자동 접속 대기와 노드 발견 실패가 반복됐다. 도메인73 일치만으로 해결되지 않았다.
사용자가 관리자 PowerShell에서 ROS 도메인73용 Hyper-V UDP 허용 규칙을 추가했다.
UDP 전용만으로도 재발했고, 큰 UDP 노드 정보 묶음이 미러 루프백 경로를 지나는 것을 관찰했다.
동일한 새 turtlesim의 대조 시험에서 기본 패킷은2회 실패, 최대1400바이트는2회 성공했다.
설정 저장 후 실제 `wsl --shutdown`을2회 수행했고 각 재시작 뒤 노드·토픽·pose 수신이 성공했다.
그 후 사용자의 종료 요청에 따라 assistant가 띄운 turtlesim·데몬·진단 프로세스를 종료 확인했다.
이 결과는 해당 PC의 검증 범위이며 WSL/Windows 내부 결함의 정확한 위치까지 확정한 것은 아니다.
