- STM32 두 모터 속도 제어를 구조체와 공통 함수로 정리

## 핵심 개념

### 파일의 역할

| 파일 | 역할 |
| --- | --- |
| `Core/Inc/motor_control.h` | 공통 자료형, 제한 상수, 공개 함수 선언 |
| `Core/Src/motor_control.c` | PWM 적용, 초기화, 정지, 측정·PI·방향 전환 구현 |
| `Core/Src/main.c` | 모터별 설정 선언, 주변장치 초기화, 100ms 함수 호출 |

`main.c`는 CubeMX 주변장치 설정과 실행 순서를 담당하고 실제 제어 계산은 모터 모듈이 담당합니다. 이번 제어는 인터럽트 콜백이 아닌 메인에서 수행합니다.

### 구조체로 설정과 상태 묶기

```text
Motor
├─ config : MotorConfig — 핀·타이머·엔코더 변환 기준
└─ state  : MotorState  — 목표·측정값·듀티·적분값·방향 상태
```

| 자료형 | 주요 멤버 | 의미 |
| --- | --- | --- |
| `MotorConfig` | `encoder_timer`, `pwm_timer`, `pwm_channel` | 사용할 타이머와 PWM 채널 |
| `MotorConfig` | `dir_port`, `dir_pin` | 방향 GPIO |
| `MotorConfig` | `encoder_bits`, `encoder_sign` | 카운터 크기와 측정 부호 보정 |
| `MotorConfig` | `counts_per_turn`, `wheel_circumference_mm` | 속도 변환 기준 |
| `MotorState` | `target_speed_mm_s`, `speed_mm_s`, `rpm` | 목표·측정 속도 |
| `MotorState` | `speed_error`, `duty_percent`, `i_output` | 제어 오차와 출력 |
| `MotorState` | `kp`, `ki` | 각 모터의 PI 이득 |
| `MotorState` | `previous_count`, `delta_count` | 모터별 이전 CNT와 측정 구간 이동량 |
| `MotorState` | `direction`, `stop_samples` | 실제 설정 방향과 정지 확인 횟수 |

같은 자료형을 사용해도 motor1과 motor2는 별도 저장 공간을 가집니다. 적분값과 이전 카운트를 공유하면 각 모터의 실제 상태에 맞는 제어가 되지 않습니다.

### 점, 주소, 포인터

```c
motor1.state.speed_mm_s;       // 구조체 변수에서 직접 접근
Motor_Update(&motor1, dt_ms);  // 모터 1의 주소 전달
motor->state.speed_mm_s;      // 함수가 받은 주소로 원본 상태 접근
```

- `Motor`는 자료형이고 `motor`는 매개변수 이름입니다. 대소문자를 구분합니다.
- `&motor1`은 motor1의 주소, `Motor *motor`는 그 주소를 받을 포인터입니다.
- 설정의 `&htim2`는 기존 HAL 타이머 핸들의 주소를 보관하며 핸들을 새로 복제하지 않습니다.
- `typedef struct { ... } Motor;`에서 마지막 `Motor`가 정의할 자료형 이름입니다.

### static과 헤더 보호

- 함수 앞의 `static`: 해당 `.c` 내부에서만 사용하는 함수로 제한합니다. `Motor_ApplyDuty()`가 해당합니다.
- 지역변수 앞의 `static`: 호출 사이에 저장값을 유지하는 의미로 사용했던 것으로, 함수의 공개 범위와는 적용 대상이 다릅니다.
- 헤더의 `#ifndef` / `#define` / `#endif`: 헤더가 여러 경로로 포함되어도 중복 정의되지 않도록 보호합니다.
- 매크로는 텍스트 치환이므로 `#define MOTOR_DUTY_LIMIT_PERCENT 50.0f`처럼 작성하고 `=`나 `;`를 붙이지 않습니다.
- 현재 상태는 메인에서만 사용하므로 volatile을 추가하지 않았습니다.

## 함수 구성과 동작

| 함수 | 공개 범위 | 역할 |
| --- | --- | --- |
| `Motor_ApplyDuty()` | `.c` 내부 static | 듀티 0~50% 제한, 상태 저장, 실제 CCR 반영 |
| `Motor_Stop()` | 공개 | 목표·적분값·정지 확인 횟수 초기화, CCR 0 적용 |
| `Motor_Init()` | 공개 | 상태 초기화, CCR 0, DIR 설정, CNT 초기화, 엔코더·PWM 시작 |
| `Motor_SetTargetSpeed()` | 공개 | 유한한 목표값 확인, ±200mm/s 제한, 0 명령 즉시 정지 |
| `Motor_Update()` | 공개 | 엔코더 변화량·속도 계산, 정지·방향 판단, PI 출력 적용 |

`Motor_Init()`의 `(MotorState){...}` 대입에서 지정하지 않은 상태 멤버는 모두 0이 됩니다. 하드웨어 설정 config는 유지됩니다. 최신 저장 소스는 **Kp=0.2, Ki=0.1**입니다. 앞선 분리 전 동시 실측에서 사용했던 **Kp=0.1, Ki=0.1**과 구분합니다.

`Motor_Stop()`은 측정 속도를 임의로 0으로 만들지 않습니다. 바퀴가 관성으로 회전하면 다음 엔코더 측정까지 실제 속도가 남을 수 있습니다. 명령 0과 물리적인 완전 정지는 다른 시점일 수 있습니다.

### 제어 계산

현재 사용한 PI 관계는 아래와 같습니다.

```text
e(t) = r(t) - y(t)
u(t) = Kp × e(t) + Ki × ∫e(t)dt
```

- e는 오차, r은 목표, y는 피드백 속도이며 단위는 mm/s입니다.
- 출력은 듀티 %, `i_output`에는 적분 출력 자체를 저장합니다.
- 구현에서는 `이전 적분 출력 + Ki × control_error × 실제 dt(초)`로 누적합니다.
- `control_error = direction × speed_error`로 현재 진행 방향 기준의 출력 부족·과다를 판단합니다.
- 출력 상한을 더 초과시키는 양의 적분, 출력 하한을 더 낮추는 음의 적분은 저장하지 않습니다.
- 방향 변경 시에는 출력과 적분값을 0으로 만들고 3회 연속 순카운트 변화가 0일 때 DIR을 바꿉니다.
- 정지·방향 변경 분기의 `return`은 같은 호출에서 PI가 출력을 다시 올리지 않도록 합니다.

공식 식 출처: [Microchip PI 제어 설명](https://onlinedocs.microchip.com/oxy/GUID-69278EBA-9F00-4CEE-8103-2998236856BD-en-US-2/GUID-68C13886-A5D4-4274-9410-D1AE3D79CFF9.html).

### 엔코더 경계 보정과 진행 방향

TIM3의 16비트 CNT는 원래 0~65535이며 음수가 아닙니다.

| 원시 CNT 변화 | 단순 차이 | 실제 변화량 보정 |
| --- | --- | --- |
| 65535 → 0 | -65535 | +65536 → +1 |
| 0 → 65535 | +65535 | -65536 → -1 |

```c
if (delta_count > 32767) delta_count -= 65536;
else if (delta_count < -32768) delta_count += 65536;
delta_count *= motor->config.encoder_sign;
```

경계 보정은 카운터 증가·감소를 해석하며 로봇의 전진을 정하는 코드는 아닙니다. 이후 encoder_sign으로 전진을 양수에 맞춥니다. 한 측정 구간의 이동량이 ±32768카운트 미만이라는 조건에서 해석합니다. 현재 배선 교환 후 두 모터 모두 HIGH 전진·양수 피드백으로 확인하여 encoder_sign=1을 사용합니다. 코드 반전과 A/B 배선 교환을 중복 적용하지 않습니다.

## main.c 연결과 시작 순서

```text
HAL_Init → SystemClock_Config
→ MX_GPIO_Init / MX_TIM2_Init / MX_TIM1_Init / MX_TIM3_Init
→ Motor_Init(&motor1) → Motor_Init(&motor2)
→ previous_tick = HAL_GetTick()
→ while 반복
   → 100ms 이상 경과했는지 확인
   → 실제 sample_dt_ms 계산
   → Motor_Update(&motor1, sample_dt_ms)
   → Motor_Update(&motor2, sample_dt_ms)
   → previous_tick = now
```

두 함수 호출은 순차적으로 실행됩니다. 엔코더 계수와 PWM 출력은 하드웨어에서 계속 수행됩니다. `>=100U`는 100ms부터 실행하고 `>100U`는 최소 101ms부터 실행합니다. 이전 tick을 계산 전에 갱신하면 시간 차이가 0이 되므로 마지막에 갱신합니다.

처음 실행한 목표 속도는 두 모터 모두 0입니다. `Motor_Init()`은 CCR을 0으로 준비한 뒤 PWM을 시작합니다.

## 실습과 결과

### 앞선 실제 두 모터 시험: 파일 분리 이전

각 목표를 약 12초 적용하고 마지막 약 4초 SWD 조회 표본을 요약했습니다. 당시 이득은 Kp=0.1, Ki=0.1입니다.

| 듀티 상한 | 목표 mm/s | 모터 1 평균 mm/s | 모터 2 평균 mm/s |
| --- | --- | --- | --- |
| 20% | 100 | 99.77 | 99.82 |
| 50% | 50 | 50.27 | 49.66 |
| 50% | 100 | 99.74 | 100.12 |

목표 100에서 듀티는 약 12%였고 각 시험 후 두 목표·측정 속도·적분값·듀티·CCR이 0임을 확인했습니다. 공중 동시 시험은 기존 20%에서도 수렴했으므로 50% 변경 때문에 이 결과가 개선됐다고 해석하지 않습니다.

이전 모터 2 단독 시험에서 양수 목표에 음수 피드백이 들어와 듀티가 20%까지 올라가는 문제가 있었고, 사용자가 엔코더 배선을 반전한 뒤 정상 부호를 확인했습니다. 이후 저속 시험에서 목표 100에 약 3~38mm/s가 나온 조건은 사용자가 바퀴를 띄우지 않은 바닥 조건이었다고 설명했습니다. 공중 시험과 부하·마찰 조건이 달랐습니다.

### 파일 분리 이후

- 두 소스와 헤더의 ARM GCC `-fsyntax-only -Wall -Wextra` 검사 통과
- CubeIDE Debug 전체 빌드 통과, 링크 입력에 motor_control.o 포함 확인
- ELF에 Motor_Init / Motor_Update / Motor_Stop과 motor1 / motor2 구조체 포함 확인
- 사용자가 새 변수 이름으로 디버깅 후 정상 동작한다고 보고함
- 최신 저장 소스(Kp=0.2, Ki=0.1)도 기록 저장 전에 문법·전체 빌드 재확인
- 기록 정리 과정에서는 보드 업로드나 모터 구동을 수행하지 않음

구조체 분리 후의 수치 로그와 바닥에서의 최종 속도 추종 성능은 별도 확인이 필요합니다. 공중 시험 통과만으로 실제 하중에서 제어가 완료됐다고 보지 않습니다.

## 디버깅 변수와 사용법

Live Expressions에 아래 표현식을 한 줄씩 추가하거나 motor1/motor2를 펼쳐 state를 확인합니다.

```c
motor1.state.target_speed_mm_s
motor1.state.speed_mm_s
motor1.state.duty_percent
motor1.state.i_output
motor2.state.target_speed_mm_s
motor2.state.speed_mm_s
motor2.state.duty_percent
motor2.state.i_output
```

목표는 100=전진 100mm/s, -100=후진, 0=정지입니다. 측정값과 제어 출력은 관찰합니다. 디버거에서 목표 필드를 직접 쓰면 Motor_SetTargetSpeed의 ±200mm/s·유한값 검사를 우회하므로 시험값 범위를 지킵니다. 실제 응용 코드에서는 목표 설정 함수를 사용합니다.

회전 중 중단점을 걸면 PWM이 계속 나갈 수 있습니다. 시험 후 두 목표를 0으로 하고 정지 상태를 확인합니다.

## 추가: 바닥 시험과 출발 떨림 조정

- 공중 ±50·100·150·200mm/s, 바닥 ±50·100mm/s를 측정했습니다. 노트북 USB 연결로 이동 공간이 좁아 이후 시험은 8초로 제한했습니다.
- +100에서 모터1 평균 77.17mm/s가 나온 시험에는 사용자 확인상 장애물이 있었습니다. 해당 시험은 자유 주행 성능 비교에서 제외했습니다.
- 출발 시 좌우 떨림을 관찰해 Kp=0.2, 0.1, 0.05를 비교했습니다. Ki=0.1은 유지했습니다.
- Kp를 낮춘 후 엔코더상의 좌우 속도 차이는 감소했습니다. 실제 차체 진동은 엔코더 속도 차이만으로 완전 해소를 판정하지 않습니다.
- Kp=0.05·0.1에서 정지 없이 50→100 목표를 변경하는 시험을 각각 정·역방향으로 반복했습니다. 각 목표를 4초씩 적용했으며 전환 직전 실제 속도는 50에 안정되지 않았습니다. 최초 95 도달과 정착 시간은 구분합니다.
- 반복한 ±100 단독 8초 시험에서는 Kp=0.1의 목표 부근 평균 오차와 속도 표준편차가 더 작았습니다. 최초 도달이 항상 더 빠르지는 않았습니다.
- 사용자 요청으로 최종 기본값을 두 모터 모두 **Kp=0.1, Ki=0.1**로 선택했습니다. 실제 학습 프로젝트의 `Motor_Init()`에 반영하고 빌드·보드 업로드·재시작 후 값을 확인했습니다. 적용 후 모터 목표·속도·적분·듀티·CCR은 모두 0입니다.
- 다음 학습은 목표 속도의 가속도 제한입니다. 요청 목표와 PI에 적용할 목표를 구분해 급격한 출발·목표 변경을 완만하게 만드는 흐름을 학습합니다. 이후 로봇 선속도·각속도 변환으로 이어갑니다.
